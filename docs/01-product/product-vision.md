# 产品愿景与范围（Proposed）

## 产品问题
现有项目常将任务规则、执行节点、重试逻辑、历史日志散落在代码和多套控制台。OTRYX Flow 要提供可验证、可观测且可部署的单一控制面，并作为 OTRYX RPC 的真实微服务样板。

## 用户画像和核心成果
| 角色 | 最关心的事情 | 可验证结果 |
|---|---|---|
| 系统管理员 | 用户、接入身份、运行配额、审计 | 能查看权限与拒绝记录，禁用危险任务 |
| 项目 Owner | 任务/工作流、成员权限、版本发布 | 可安全发布并回滚定义版本 |
| 操作员 | 手动执行、取消、重试、日志排查 | 不绕过项目权限，结果可追溯 |
| 观察员 | 查看执行、监控、告警 | 无法更改任务和执行状态 |
| Worker 开发者 | 使用 SDK 实现 Java Handler | 启动、领取、执行、停止与重试语义明确 |
| 演示访客 | 在浏览器体验系统 | 只运行受限内置任务，无敏感操作 |

## V1 的用户旅程
创建项目 → 创建任务 → 绑定 Java Handler → 设置 Cron/时区 → 在可视化 DAG 中连线 → 校验并发布版本 → 启动执行 → 查看节点状态/运行日志/失败原因 → 重试或取消 → 查看告警和审计。

## 首发硬边界
1. 可信 Java Handler，缺省不开通匿名执行；开放任务脚本的能力转为将来的独立隔离执行器。
2. 单区域部署；允许同区域多个 Scheduler/Dispatcher/Worker 实例；多机房故障转移不属于 V1。
3. 使用至少一次执行模型，外部副作用幂等责任由任务作者/业务系统承担。
4. REST 面向外部用户；OTRYX RPC 面向内部业务进程；执行结果和 Outbox 落库不依赖 RPC 返回即成功。
5. 演示环境有独立权限和配额，不能直接对公网开放执行自定义 Java 类、任意网址或系统命令。

## 成功衡量
M1：真实两进程 RPC 链路通过；M2：触发/失联/重试可回放；M3：网页发布 DAG 与任务状态可核验；M4：真实 mTLS/权限闭环；M5：可重复性能与故障证据；M6：从零部署可访问 HTTPS 站点。容量 SLO 需指定固定环境后冻结，不先填伪精确数字。
