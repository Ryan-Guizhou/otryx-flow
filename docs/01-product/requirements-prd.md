# OTRYX Flow 产品需求文档 PRD v0.1（Proposed）

**基线日期：2026-10-23**。当前为待开发的产品规格；每个 `FR-XXX` 都必须通过 [验收矩阵](../06-testing/acceptance-plan.md) 定义可重复的验证方法。

## 1. 背景、目标和非目标
问题：调度链路故障难恢复、工作流状态分散、日志难检索、执行器扩容和安全边界不清晰。
目标：前后端完整、可部署、能执行可信任务、可靠恢复、调用真实 OTRYX RPC、具备审计证据。
非目标：通用 Exactly Once、任意脚本 SaaS、跨云多活、全语言 SDK、用户可自选数据库执行 SQL。

## 2. 用户角色
`SYSTEM_ADMIN` 系统管理员；`PROJECT_OWNER` 项目所有者；`OPERATOR` 操作员；`VIEWER` 只读；`DEMO_GUEST` 受限演示。Worker 采用**机器身份**，不能使用浏览器用户身份直接取得内部控制 RPC 权限。

## 4. 业务规则与边界
- 逻辑触发唯一键建议 `(schedule_id, revision, scheduled_fire_at_utc)`；手动触发使用调用者提供的幂等键。
- 同一个 DAG 版本发布后内容不可修改；回退指向已有版本或生成新的发布指针，不改变在运行实例的 Revision。
- “成功写入分发任务”与“Worker 执行成功”是不同状态。服务间 RPC 应答丢失通过业务去重、Outbox 和对账恢复。
- 失败后可能重新执行 Handler；文档和 API 不得虚称物理意义的恰好一次。
- 任务日志和输出按项目权限访问；越权请求不能通过推测 ID 读取。

## 5. 依赖与风险
- 前置：OTRYX RPC 实际 Starter API、跨 JVM/应用级 Registry、安全 Profile 和版本兼容矩阵需要在 M1 锁定提交并验证。
- MySQL 必须支持事务、唯一约束与可验证的 `SKIP LOCKED` 语义；使用 `READ COMMITTED` 的锁领取路径应实测。
- Worker 执行可信 Java 代码；进程崩溃可能发生外部副作用已提交但回执丢失，必须接入稳定的幂等键。
- 公网 Demo 的容器隔离、安全配额和日志清理必须在 M6 前完成。

## 6. 待冻结的产品决策
1. 工作流首发条件分支表达能力限定为安全的 JSON 字段比较与 AND/OR，不开放通用脚本。
2. 通知渠道首发站内通知，Webhook/邮件作为 P1，防止公网回调 SSRF。
3. 多租户 V1 使用项目级隔离；组织级强租户体系、租户自带密钥属于未来版本。
4. 性能门槛应在 M5 前声明固定测试环境和目标值，在 [性能文档](../06-testing/performance-plan.md) 中冻结。
